01 — THE FOUNDATIONA clean beginning

The Classic keyboard still felt right. Its software no longer did: SSH was unreliable after root, and Android apps lingered on a loading screen. The owner chose a clean reflash without backup. We rebuilt from a known baseline, recording what each step actually proved.

On Windows, this session used the Z30 STA100-series stock 10.3.3.3216 autoloader compatible with this Classic. Stock came first, followed by the AutoRoot v3 user filesystem built from that exact source, then its matching radio. All three operations completed, and the root update log finished successfully. The root image is not a complete stock firmware package.

Let each step produce evidence before handing it the next one.

Reading the downloaded patch and startup script exposed a small but decisive detail: this build checks use.sshd, rather than the use.ssh found in some instructions. Root and SSH markers were enabled before building, and a public key was included in the payload. Private keys stayed on the computer.

touch /var/rootdata/use.root
touch /var/rootdata/use.sshd

After reaching the desktop, the owner connected Wi-Fi and enabled Development Mode. Background initialization needed time, but a timer alone could not establish service health. The detailed Windows notes preserve the build commands and sequence.

02 — A SHELL THAT ANSWERSBeyond an open port

Development Mode and SSH are separate interfaces. An early BB10 MultiTool connection provided a path that depended on the bridge process staying alive. From Term49, we entered root, launched a separate daemon, and checked both port reachability and actual authentication from Windows.

__root
/usr/sbin/sshd -e -f /var/etc/ssh/sshd_config -h /var/etc/ssh/ssh_host_rsa_key

Some failures were typing errors with specific consequences: a trailing slash after the executable caused “Not a directory”; AuthorizedKeyFile was rejected because the setting is AuthorizedKeysFile. Missing host keys required checking the phone's key paths and permissions.

Key authentication worked before password authentication did. A configuration flag alone could not fix an account-verification mismatch. The successful password branch used an original OpenSSH 7.1p2 executable extracted from BerryCore, with QNX account overlays and path trust handling. The complete BerryCore environment was not installed first.

The cost of legacy compatibility. Traditional DES crypt authenticated in this build; MD5 attempts did not. DES considers only the first eight password bytes and offers weak protection. Prefer your own key and keep legacy root SSH off the public internet. The password reference documents the reconstruction and its limits.

03 — BEHIND THE PROGRESS BARConfiguration the runtime refused

Settings had installed, yet remained on its loading screen. Processes and logs showed Android init and resmgr, without a healthy zygote or system_server. The useful clue was explicit:

init: skipping insecure file '.../native/default.cfg'
init: skipping insecure file '.../native/init.cfg'
init: skipping insecure file '/system/build.cfg'

These configuration files were set to 777 in this installation. Android init skipped them as insecure. After discovering the actual Android application directory, we changed only default.cfg, init.cfg, system/build.cfg and autolaunch.cfg to 644, retaining their owners. We did not recursively change /apps.

Stopping the identified Android processes and reopening Settings brought up zygote, installd and SystemServer. First-boot scanning and dexopt still took time. Once the internal installation queue had finished, the owner closed the app card, reopened it and confirmed that Settings entered its page.

This device still runs Android 4.3 / API 18, primarily armeabi-v7a. Root does not upgrade the runtime to modern Android. An old NetEase Cloud Music APK installed, but password login still returned a server error. That cloud-login issue remains unresolved.

04 — THE INSTALLER'S IDENTITYUse the role the installer expects

Windows uploaded the packages; the phone's PPS installer took over. Root alone did not provide the right role for every PPS operation. /bin/on -u upd /bin/sh supplied the installation identity needed in this session.

/bin/on -u upd /bin/sh
# Submit action, package_location and extras for a unique job.
# Wait for progress::100 AND result::success.

All eight batch jobs returned success. Filenames were sometimes misleading: Angry-Birds_1.4.1 identified itself as Angry Birds Star Wars.

The games were not individually launched, so touch controls, screen layout and online services remain unverified. After confirmed installation, thirteen known uploaded BAR copies were removed, reclaiming about 780 MiB. Installed applications do not depend on those upload copies. Root maintenance payloads and unknown system files were retained.

The repository includes a reusable skill preserving the details most likely to be misread: matching firmware sources, use.sshd, QNX overlays, the upd role, Android configuration modes, and the difference between listening, authentication, installation and execution.

Mac image building and flashing were not performed.

06 — THE MAC CHAPTERA shell, a keyboard, another beginning

The Mac session began with an already reflashed, rooted Classic. On Apple Silicon we connected over Wi-Fi, enabled the device’s legacy RSA host-key algorithm for that connection, corrected the private key’s local permissions, and authenticated. No image was built or flashed on the Mac.

BerryCore 0.90.1 was downloaded from its official release, checked against the published SHA-256 digests, then transferred using traditional SCP. A successful unzip was only the beginning: QNX rejected scripts and executables as untrusted. File-specific pathtrust restored the environment and several tools, including Git, curl, nano and Vim. The bundled GCC file was a Git LFS placeholder; Bash remained unresolved.

# Short commands added to this device’s Term49 profile
sshon
sshstatus

Term49 has its own home directory. We added an automatic BerryCore profile there and moved SSH process checks into the root helper to avoid sandbox errors. A reboot later erased file trust; a restore step was added to the existing root startup chain, with a backup. That hook still needs a reboot regression check.

Still open: Python 3.11 prints its version, but extension imports fail. pip and the setup web page are not working. The full Mac notes distinguish current checks from unverified reboot behavior.
