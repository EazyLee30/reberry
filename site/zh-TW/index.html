01 — THE FOUNDATION先把底座恢復乾淨

本次使用者從 BerryLife 的 Pre-rooted Autoloaders v3 指南取得工具與刷機資源。該頁提供 v3 工具和原廠 ROM 的入口，並註明原作者 Oleksandr；本倉庫透過來源頁面連結資源，不託管韌體。

Classic 的鍵盤還好好的，系統卻已經失去配合：root 後的 SSH 不穩定，Android 應用又停在加載頁面。使用者決定不備份，授權清空重刷。我們回到同一份原廠固件，再建立可解釋的狀態。

這次使用適配 Classic 的 Z30 STA100 系列 10.3.3.3216 stock autoloader。Windows 上先刷 stock，再刷由同一來源構建的 AutoRoot v3 用戶文件系統，最後刷配套 radio。三次工具都完成，隨後 root 更新日誌也記錄完成。root 鏡像不是完整原廠包，同源底座是這條路徑的前提。

先讓每一步有證據，再把下一步交給它。

構建前讀取 patch 與啓動腳本，比複述一份教程更有用。本次腳本實際檢查的是 use.sshd，某些說明中寫成 use.ssh。我們啓用了 root、SSH 標誌，並把自有公鑰放進 payload。私鑰留在電腦；公開記錄裏不保存憑據。

touch /var/rootdata/use.root
touch /var/rootdata/use.sshd

開機到桌面後，連接 Wi-Fi、打開開發模式，等待後臺初始化。固定等待時間可以作參考，但完成與否仍要看服務和日誌。完整構建參數與命令見 Windows 操作記錄。

02 — A SHELL THAT ANSWERS端口打開，只是故事的開始

開發模式和 SSH 是不同的接口。早期通過 BB10 MultiTool 建立的連接，還會隨連接進程退出而消失。手機端用 Term49 進入 root 後，我們單獨啓動 SSH，並從 Windows 檢查端口和真實認證。

__root
/usr/sbin/sshd -e -f /var/etc/ssh/sshd_config -h /var/etc/ssh/ssh_host_rsa_key

最早的錯誤裏有兩處手輸細節：二進制路徑末尾多了斜槓，會得到“Not a directory”；配置項寫成 AuthorizedKeyFile 會被拒絕，正確拼寫是 AuthorizedKeysFile。主機密鑰缺失，則需要檢查設備上的密鑰路徑與權限。

密鑰認證走通後，密碼認證又成爲單獨的問題。只改一個配置開關仍然不夠：這臺原生服務沒有驗證成功所需的 root 密碼。最後從 BerryCore 包中提取原始 OpenSSH 7.1p2，結合 QNX 的賬戶 overlay 和路徑信任機制，完成了獨立服務的密碼登錄。這個階段沒有先安裝整個 BerryCore。

歷史兼容的代價。本次替代服務走通的是傳統 DES crypt；MD5 嘗試失敗。DES 只考慮密碼前八個字節，保護能力很弱。它作爲舊系統排障記錄保留，默認仍應使用自有密鑰，避免把舊 root SSH 暴露到互聯網。閱讀完整限制與重建思路 →

03 — BEHIND THE PROGRESS BAR進度條後面，是被拒絕的配置

Settings 已安裝，卻一直卡在後面的進度條。查看進程和系統日誌時，Android 的 init 和 resmgr 出現了，zygote 與 system_server 卻沒有正常啓動。真正有方向的日誌，是這句：

init: skipping insecure file '.../native/default.cfg'
init: skipping insecure file '.../native/init.cfg'
init: skipping insecure file '/system/build.cfg'

本次配置文件被設成了 777，Android init 因爲權限過寬而跳過。我們發現實際 Android 應用目錄後，僅把 default.cfg、init.cfg、system/build.cfg 與 autolaunch.cfg 改爲 644，保留所有者。沒有遞歸更改整個 /apps。

停止已定位的 Android 相關進程、重新打開 Settings 後，zygote、installd 和 SystemServer 開始出現。首次掃描和 dexopt 仍需等待；使用者關閉卡片再重新打開，最終確認進入了設置頁面。

這臺設備的 Runtime 仍是 Android 4.3 / API 18，主要 ABI 爲 armeabi-v7a。root 不會把它升級成現代 Android。網易雲舊版可安裝，但密碼登錄依然報服務器錯誤；這項雲端登錄問題仍未解決，我們沒有把它寫成恢復成功。

04 — THE INSTALLER'S IDENTITYroot，也要用對安裝身份

Windows 負責上傳文件，手機裏的 PPS 安裝器接手。最實用的發現是：以 root 直接寫 PPS 仍可能遇到權限問題；通過 /bin/on -u upd /bin/sh 使用安裝器身份，就能提交任務並讀取狀態。

/bin/on -u upd /bin/sh
# 對獨立任務寫入 action、package_location、extras
# 等待 progress::100 和 result::success

這次八個 BAR 的任務全部返回 success。文件名也不總是軟件名：名爲 Angry-Birds_1.4.1 的包，實際識別爲 Angry Birds Star Wars。

應用本次狀態
Playepub / Plants Vs Zombies / Cut the Rope 2安裝器 success
Asphalt 6 / Angry Birds Star Wars / Angry Birds安裝器 success
2048 / Minion Rush安裝器 success
Settings使用者確認進入頁面

沒有逐一運行遊戲，因此觸控、畫面比例、舊網絡服務的兼容性還不能下結論。安裝成功後，刪除這次上傳的十三份暫存 BAR，釋放約 780 MiB。應用本體不依賴這些上傳副本；root 自帶的維護 payload 和未知系統文件保留。

05 — PASS IT FORWARD讓下一位 agent 接得住

倉庫附帶可複用 skill，把這次最容易誤判的邊界留下：固件同源、use.sshd、QNX overlay、upd 角色、Android 配置權限，還有“監聽、認證、安裝和運行是不同狀態”。

複製這段 prompt
請讀取 https://github.com/EazyLee30/reberry ，先閱讀 README.md 和 skills/blackberry-bb10-recovery/SKILL.md。
結合我的電腦系統、設備型號、固件與日誌，協助恢復我擁有的 BB10 設備。
先發現當前狀態，不要默認重刷；刷寫前確認清空授權及 stock/root 同源。
使用我自己的密鑰。不要發佈密碼、私鑰、設備標識、個人地址或原始日誌。
分別確認 SSH 監聽與認證、Android 系統服務、安裝器 success 和應用實際運行。
若在 Mac 上執行，只記錄真實執行過的操作，閱讀 docs/recovery-flow.md#next-checks 並補充 Mac 章節。

新增 Mac 實測手記：從 SSH 連接，到 BerryCore 安裝、Term49 自動載入與 SSH 短命令。重啟後檔案信任遺失，已加入恢復步驟，但重啟回歸仍待驗證。Python 擴充、pip、setup 和 Bash 尚未解決；Mac 鏡像構建與刷寫沒有執行。

06 — THE MAC CHAPTER讓終端接住下一次開機

Mac 接手時，Classic 已由使用者重新刷機、完成 root。我們從 Apple Silicon Mac 透過 Wi-Fi 登入 SSH，為這臺舊設備單獨啟用 RSA 主機密鑰相容選項，修正私鑰本地權限，再驗證認證與遠端命令。Mac 上沒有構建鏡像或刷寫手機。

官方 BerryCore 0.90.1 下載後先比對 SHA-256，再用傳統 SCP 上傳。解壓完成，卻不代表程式能執行：QNX 拒絕不受信任的腳本和二進位檔案。逐檔案設定 pathtrust 後，Git、curl、nano、Vim 等工具執行通過。GCC 的內建套件只是 Git LFS 佔位檔案，已跳過；Bash 仍未解決。

# 為這臺設備的 Term49 配置的短命令
sshon
sshstatus

Term49 的 HOME 屬於應用自身，我們在實際發現的 data 目錄寫入自動載入配置。SSH 狀態檢查改在 root helper 中執行，避免普通使用者掃描其他程序時刷屏。隨後重啟讓檔案信任消失，又在現有 root 啟動鏈加入恢復步驟並保留備份；這個開機修復尚待再次重啟驗證。

還沒有走通：Python 3.11 能顯示版本，但擴充模組載入失敗，pip 和 setup 網頁仍不可用。完整 Mac 記錄逐項區分已驗證、失敗與待驗證的狀態。

Classic，真的還在用

三張來自這台 Classic 的實拍：瀏覽網頁、打開遊戲頁面，以及 Term49 裡的 BerryCore。記錄當時的畫面，不把它當作效能測試。
